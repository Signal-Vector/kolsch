# QoL — Tool output truncation, persistence, and line-based read

**Draft 0.1** *(four-step build plan, dependency-ordered, each step shipping its own PR with dev + reviewer prompts. Borrows three patterns from Claude Code that meaningfully improve agent ergonomics on long outputs and large files.)*

> Current state:
> - `bash` truncates stdout/stderr at 64 KiB each with a
>   `[... truncated N bytes]` suffix. Content past the cap is
>   gone — no recovery path.
> - `read_file` refuses outright on files larger than
>   `max_bytes` (default 1 MiB), raising `file.too_large`.
>   Model gets nothing useful.
> - `read_file`'s interface is byte-based; LLMs reason
>   naturally in line ranges and frequently fall back to
>   `cat <path>` via `bash` instead — bypassing the platform's
>   path policy and bloating context with full-file dumps the
>   model didn't actually want.
>
> Three small upgrades close all three gaps:
>
> 1. **Persist bash overflow to a workspace tmp file** + return
>    the path. Model can `read_file` the persisted output with
>    offset/limit to drill in.
> 2. **Line-based `read_file` with `offset`/`limit`** as the
>    primary interface (with `max_bytes` retained as a defensive
>    cap). Updated description that makes the cat-via-bash
>    fallback obviously wrong.
> 3. **Soft truncation on `read_file`** — read what fits, return
>    partial content + continuation info instead of raising on
>    over-limit files.
>
> Combined effect: the model never hits a dead end on tool
> output. Always gets a partial answer + a path forward.

---

## Part 0 — Why this matters

Three problems with today's behavior:

### 0.1 bash overflow loses information

`src/cli/_starter_bundle/kolsch/tools/bash.py:163-168` truncates
at 64 KiB and drops the tail. Common cases that exceed this:

- `find . -type f` in a non-trivial tree.
- `git log -p` on any active branch.
- `pytest -v` on a moderate test suite.
- `npm install` output.

When the relevant signal is past 64 KiB, the model is blind to
it with no recovery. It either retries with `... | head -n N`
guesswork (wasting turns) or hallucinates a plausible
continuation (wasting accuracy).

### 0.2 read_file refuses large files entirely

`src/cli/_starter_bundle/kolsch/tools/read_file.py:117-118`
raises `file.too_large` when size > `max_bytes`. The model
gets nothing — not even the file's structure. Common cases:

- A 2 MB log file the user just dropped in the workspace.
- A long pyproject.toml after dependency expansion.
- An autogenerated config the user wants to inspect.

The hard refuse forces the model into bash workarounds
(`head`, `tail`, `wc -l`) that defeat path-policy
enforcement.

### 0.3 LLMs prefer `cat` over `read_file`

Reported by user observation across sessions: even with the
current tool description explicitly saying "Prefer this over
running `cat` via `bash`," models still reach for `cat` first.
Likely causes:

- Training bias: `cat <path>` is overwhelmingly common in
  training data; `read_file({path: ...})` rare.
- Interface ergonomics: `cat` accepts a path; `read_file`
  accepts a JSON object. The mental cost is higher.
- No line semantics: `read_file` returning whole files (or
  refusing) doesn't compose with the model's natural
  "show me lines 50-100" thinking.

The model bypassing `read_file` is a real safety + budget
concern: `cat` is unbounded, doesn't respect path policy via
the file tools' contract, and dumps potentially huge content
into context.

## Part 1 — Decisions locked

From the conversation that opened this ticket:

1. **Persisted output goes to a workspace tmp file.** Specific
   location: `<workspace>/.platform/tool-outputs/<session_id>/<tool_call_id>.<stream>.txt`.
   Inside the workspace so existing path policy permits the
   subsequent `read_file`. Session-scoped for cleanup
   addressability.

2. **`read_file` becomes line-based** as the primary interface.
   New schema: `path` + `offset` (line, 0-indexed) + `limit`
   (lines). `max_bytes` retained as a defensive cap (refuses
   if any single line exceeds it — guards against e.g.
   minified binary masquerading as text).

3. **Soft truncation** on `read_file`. Files exceeding the
   line-budget OR the byte-budget return partial content
   with continuation metadata: `{content, lines_returned,
   total_lines, next_offset}`. No `file.too_large` raise for
   the common over-limit case.

4. **Description rewording** for both tools. The new
   `read_file` description leads with a line-based example
   and names `cat`/`head`/`tail` explicitly as anti-patterns.
   The `bash` description gets a brief redirect for those
   specific commands.

5. **No bash-side detection of `cat`/`head`/`tail`** in this
   QoL. Description-only nudge for v1; if model behavior
   doesn't change after the rewording lands, a follow-up
   ticket can add active detection. Don't pre-optimize.

6. **No automatic cleanup of persisted-output files** in this
   QoL. The session dir is small; persisted outputs accumulate
   per session. Cleanup happens when the user removes the
   session dir manually OR via a follow-up `kolsch sessions
   purge` command (future scope).

## Part 2 — Acceptance criteria

The QoL is shipped when **all** hold:

1. **bash persists oversize streams.** Stdout or stderr
   exceeding the threshold gets written to
   `<workspace>/.platform/tool-outputs/<session_id>/<tool_call_id>.<stream>.txt`.
   The tool's return shape gains `stdout_persisted_to` and/or
   `stderr_persisted_to` fields populated only when overflow
   occurs.

2. **bash preview-on-overflow.** The returned `stdout` /
   `stderr` strings show the FIRST N bytes (per Step 1's pick
   — recommended: keep 64 KiB) AND end with
   `[... full output at <path>; N more bytes; use read_file
   with offset/limit]` so the model sees the path inline.

3. **read_file accepts line-based offset/limit.** New args:
   `offset: int = 0` (line number, 0-indexed), `limit: int =
   2000` (max lines to return). `max_bytes` retained as
   defensive cap (default 1 MiB; refuses only if a single
   line exceeds the cap — Step 1 confirms this is the right
   semantic).

4. **read_file soft-truncates instead of refusing.** A file
   larger than the line budget returns:
   `{content: "...", lines_returned: N, total_lines: M,
   next_offset: N, truncated: true}`. Files within budget
   return the same shape with `truncated: false` and
   `lines_returned == total_lines`.

5. **read_file output is line-numbered.** `cat -n` style:
   each line prefixed with `<right-aligned-number>\t<line>`.
   Helps the model reason about ranges and reference
   specific lines.

6. **Tool descriptions updated.** Both tools' descriptions
   are rewritten per Step 1's wording pick. `read_file` leads
   with a line-based example; `bash` description explicitly
   redirects `cat`/`head`/`tail`/`wc -l` to `read_file`.

7. **Persisted-output files are readable by read_file**
   without authz friction (they live under the workspace,
   covered by existing path policy).

8. **No breaking change for existing agents.** Agent configs
   referencing `read_file` continue to work. Old YAMLs that
   relied on `max_bytes` semantics are coerced: the field is
   retained, just with the new "single-line cap" meaning.

9. **Regression tests cover the seven paths.** Persist on
   stdout overflow; persist on stderr overflow; persist on
   both; read_file line range; read_file soft truncation;
   read_file line numbering; bash + read_file composition
   (bash overflows, read_file picks up the persisted path).

10. **Manual e2e demonstrates the user-facing improvement.**
    A chat session asks the agent to "look at the test
    output" for a noisy `pytest` run; the agent calls bash,
    gets the overflow notice, reads the persisted path with
    a sensible offset/limit, and surfaces a useful answer.

### Explicitly out of scope

- **Active detection of `cat`/`head`/`tail` in bash.** v1
  uses description-only nudge.
- **Automatic cleanup of persisted-output files.** Manual
  cleanup or future `kolsch sessions purge`.
- **read_file streaming for very-large files.** Refuses
  single-line >max_bytes; everything else fits in the
  partial-read pattern.
- **write_file changes.** Out of scope; this QoL is
  read-side ergonomics.
- **list_files changes.** Same.
- **Image/PDF/Jupyter read support.** Claude Code does these;
  kolsch doesn't yet. Future scope.
- **Compositional output between tools** (e.g., tool A's
  result auto-piped to tool B). Out of scope.

## Step 3 — read_file: line-based + soft truncation + new description

### Developer prompt

```
[standing instructions]

Step 3 — Rebuild read_file's interface.

Read first:
- Step 1's writeup (return shape pinned).
- Step 2's PR (for the persisted-output handoff the new
  read_file description references).
- src/cli/_starter_bundle/kolsch/tools/read_file.py.

Tasks:

1. New ReadFileArgs:
   class ReadFileArgs(BaseModel):
       path: str = Field(description=...)
       offset: int = Field(
           default=0,
           ge=0,
           description="Line offset (0-indexed). Use next_offset from a prior call to continue."
       )
       limit: int = Field(
           default=2000,
           ge=1,
           description="Maximum number of lines to return. Default 2000."
       )
       max_bytes: int = Field(
           default=1_048_576,
           ge=1,
           description="Single-line byte cap. Lines longer than this raise file.line_too_long (Recoverable). Default 1 MiB — guards against binary masquerading as text."
       )

2. New return shape (dict, NOT bare string):
   {
       "content": str,           # cat -n style numbered lines, joined with "\n"
       "lines_returned": int,
       "total_lines": int,
       "next_offset": int | None,  # None when truncated == false
       "truncated": bool,
   }

   - When the read fits within `limit` from `offset`:
       total_lines = N
       lines_returned = N - offset
       truncated = False
       next_offset = None
   - When the read is bounded by `limit`:
       lines_returned = limit
       truncated = True
       next_offset = offset + limit (so the model can call
                     read_file again with this offset to
                     continue).

3. Implementation outline:
   - Read the file line-by-line (use Path.read_text then
     splitlines(keepends=False) — simple + correct for
     UTF-8 text).
   - If any single line's byte-length > max_bytes, raise
     file.line_too_long (new PlatformError — Step 1 confirmed
     this naming).
   - Slice lines[offset:offset+limit].
   - Format each line as f"{i:>{width}}\t{line}" where i is
     1-indexed line number and width is len(str(total_lines)).
   - Join with "\n"; append trailing "\n".
   - Return the dict.

4. Add file.line_too_long error class.
   - src/errors/tools.py (or wherever similar tool errors live).
   - Level: Recoverable (one bad line shouldn't kill an
     exchange).
   - detail: {path, line_number (0-indexed), line_byte_length, max_bytes}.

5. Delete the file.too_large refuse path.
   - The old size > max_bytes check raised file.too_large.
     With soft truncation, that's no longer the right
     behavior. Files larger than max_bytes (in total) are
     fine; only single lines > max_bytes trigger the new
     file.line_too_long.
   - Keep file.too_large in the error catalog (might be
     used elsewhere), but it's no longer raised from
     read_file.

6. Tool description — paste Step 1's draft verbatim.
   - Verify the description includes ALL the wording Step 1
     pinned: line-based example, anti-pattern call-out for
     cat/head/tail/less/wc, persisted-output handoff,
     directory + binary disclaimers.

7. Unit tests:
   - test_read_file_default_returns_numbered_lines:
     small file; content contains "1\t..."; total_lines
     matches; truncated False; next_offset None.
   - test_read_file_offset_limit_paginates:
     200-line file; offset=50 limit=100; content has
     lines 51-150; truncated True; next_offset 150.
   - test_read_file_eof_within_limit:
     50-line file; offset=0 limit=100; truncated False;
     lines_returned 50.
   - test_read_file_line_too_long_raises:
     file with one 2 MiB line; max_bytes=1 MiB; raises
     file.line_too_long with the right detail fields.
   - test_read_file_large_file_soft_truncates:
     10000-line file; offset=0 limit=2000 (defaults);
     truncated True; next_offset 2000; total_lines 10000.
     This is the case that previously raised file.too_large.

8. NO change to:
   - bash (Step 2).
   - write_file, list_files.
   - The path policy / authz.

Scope: ~120 LOC code + ~150 LOC tests.
```

## Part 9 — Step 1 writeup (pinned design)

*(filled by the Step 1 verification pass — 2026-06-03. Locks
schema/path/descriptions before any code lands.)*

### 9.1 ctx.session_id availability

Confirmed available at tool-call time. Construction sites:

- `src/engine/observers.py:217-223` — `_ObservedToolHandle.__call__`
  builds `ToolContext(... session_id=self._session_id, ...)` for
  every model-driven tool call. `self._session_id` is set in the
  ctor from the parent thread's session.
- `src/engine/engine.py:967-973` — the force-invoke read path
  (skill auto-read) builds the same `ToolContext` with the active
  session id.

`session_id: SessionId` is REQUIRED on `ToolContext`
(`src/tools/decorator.py:53-54`), so the field can never be None at
invocation time. Pre-flight contexts that never reach a tool don't
matter — the persistence path only runs INSIDE a tool call.

### 9.2 Path policy reachability — `.platform/` is denied by default

**The plan's proposed path `<workspace>/.platform/tool-outputs/`
is NOT reachable.** `src/assets/platform_config.py:86` ships
`denied_paths: [".env", ".platform/"]` in the default
`file_access` config. The path policy evaluates denies first
(`src/files/policy.py:182-189`), so any read_file call against
`.platform/tool-outputs/...` returns `file_access.denied` —
defeating the entire handoff.

**Pick: `<workspace>/logs/tool-outputs/<session_id>/<call_id>.<stream>.txt`.**

Rationale:
- `logs/` is in the default `allowed_paths`
  (`src/assets/platform_config.py:78-86`) — no migration cost.
- Persisted tool output IS log-like (transient, per-session,
  diagnostic). Sits next to other operational artifacts.
- `data/` was the runner-up but it carries the connotation of
  user/agent persistent data, which this isn't.
- `sessions/` was a non-starter because session files are a flat
  layout (`sessions/ses_<uuid>.jsonl`) — creating
  `sessions/<id>/...` as a directory would collide with the file
  naming convention.

### 9.3 Persistence-dir creation strategy

**Lazy in `bash.py` at write time.** `Path.mkdir(parents=True,
exist_ok=True)` inside the first overflow write. Justification:
- Sessions that never overflow get no empty dirs.
- The tool that owns the dir owns its creation — no engine-level
  coordination needed.
- Idempotent under concurrent calls (Python's mkdir/exist_ok is
  safe).

### 9.4 Threshold pick

**Keep 64 KiB per stream for v1.** The `_OUTPUT_TRUNCATE_BYTES`
constant in `bash.py:34` and `builtins.py:63` is locked. The change
is "what happens AT overflow," not "where overflow starts."

### 9.5 `read_file` schema — pinned

Args:

```python
class ReadFileArgs(BaseModel):
    path: str
    offset: int = Field(default=0, ge=0)        # 0-indexed line number
    limit: int = Field(default=2000, ge=1)      # max lines to return
    max_bytes: int = Field(default=1_048_576, ge=1)  # single-line cap (NEW MEANING)
```

Return shape (always a dict — NOT a bare string anymore):

```python
{
    "content": str,                # cat -n style, lines joined with "\n", trailing "\n"
    "lines_returned": int,         # count of lines in `content`
    "total_lines": int,            # total lines in the file
    "next_offset": int | None,     # offset to pass on the next call; None when truncated == False
    "truncated": bool,             # True when the read was bounded by `limit`
}
```

Semantics:
- When `offset + limit >= total_lines`: `truncated = False`,
  `next_offset = None`, `lines_returned = total_lines - offset`
  (clamped at 0 if offset is past EOF).
- When `offset + limit < total_lines`: `truncated = True`,
  `next_offset = offset + limit`, `lines_returned = limit`.

### 9.6 Single-line-too-long semantic — new error class

**Pick: new `FileLineTooLong` class with code `file.line_too_long`,
Level.RECOVERABLE.** Lives in `src/errors/file_handling.py`
alongside `FileTooLarge`.

Detail fields: `{path, line_number (0-indexed), line_byte_length,
max_bytes}`.

Justification: a separate code is cheap and makes the model's
reaction unambiguous ("one bad line" vs. "file too big overall").
Reusing `file.too_large` with a `detail.reason="single_line"`
would force every consumer to branch on detail — and the catalog
already has room for the new code.

`FileTooLarge` is RETAINED in the catalog and class list for
future callers but is NO LONGER raised by `read_file`.

### 9.7 Line numbering format

`cat -n` style: `f"{i:>{width}}\t{line}"` where `i` is the
1-indexed line number and `width = len(str(total_lines))` so the
column is consistent across a paginated read. Trailing `\n` after
the final line. No escaping of the line text itself.

Worst case for `total_lines` width: a 10M-line file produces an
8-wide column, costing ~9 bytes per line for the prefix. For a
2000-line page that's ~18 KB of prefix — acceptable. No silent
cap; if a future need arises, file a follow-up.

### 9.8 tool_call_id threading — extend `ToolContext`

The persistence path needs `tool_call_id` for the filename. It is
generated in `src/engine/observers.py:200` but NOT currently
passed to `ToolContext`.

**Pick: add an optional field `tool_call_id: str | None = None` to
`ToolContext`** and populate it at the two construction sites in
the engine (observers.py:217, engine.py:967). Tests / other
construction sites stay byte-identical (field is optional).

Fallback when None (e.g., a test constructing a bare ToolContext):
bash uses `tc_anon_<uuid4>` so the persistence path still works.

### 9.9 `read_file` description — FINAL TEXT (paste verbatim in Step 3)

```
Read a UTF-8 text file by line range. Returns the requested lines
(default: first 2000) with cat -n style line numbers, plus
pagination metadata. Use this for ANY file inspection — code,
config, logs, YAML.

Examples:
  read_file({path: "src/main.py"})
    — first 2000 lines, numbered.
  read_file({path: "src/main.py", offset: 50, limit: 100})
    — lines 51 through 150 (offset is 0-indexed).
  read_file({path: "logs/tool-outputs/.../bash.stdout.txt"})
    — read a persisted bash output (see the bash tool).

DO NOT use ``bash`` with ``cat``, ``head``, ``tail``, ``less``,
or ``wc -l`` to inspect files. Those bypass the workspace path
policy AND dump unbounded content into context. ``read_file``
enforces the policy and returns structured pagination so you can
drill in without bloat.

For directories use ``list_files``. For binary files (images,
archives) the UTF-8 decode will produce garbage — don't.

Returns ``{content, lines_returned, total_lines, next_offset,
truncated}``. When ``truncated`` is true, pass ``offset:
next_offset`` to continue. Raises ``file.line_too_long`` if any
single line exceeds ``max_bytes`` (default 1 MiB — guards against
binary masquerading as text). Raises ``file.not_found`` /
``file.access_denied`` for the usual reasons.
```

### 9.13 Cross-cutting note — TWO read_file implementations

There are TWO source-of-truth implementations of `read_file` and
`bash`:

1. **Bundle tools** at `src/cli/_starter_bundle/kolsch/tools/{read_file.py, bash.py}` — what `kolsch setup` writes into a workspace.
2. **Built-in factories** at `src/tools/builtins.py` — what `make_read_file` / `make_bash_v2` produce when an agent registers `builtin_names=["read_file", ...]`.

Both serve the same logical tool name and must move together to

agent behave differently. Steps 2 + 3 will update BOTH. The Phase

backward compat.
